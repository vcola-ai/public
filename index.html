How the spec is organised

The single source of truth is specs/payroll.spec.yaml (~4,800 lines, ~200 KB). It declares the entire product as data — entities, enums, records, workflows, async integrations, authorisation, and even the prose intent of each mutation — and the TPS framework's codegen turns it into a running Kotlin / GraphQL service.

📄
payroll.spec.yaml
Declarative spec — entities · enums · workflows · async work · authz · implementationIntent
🧬
Kotlin DSL
Generated DSL: ProductSpec → EntitySpec / WorkflowSpec / AsyncWorkSpec
⚙️
Runtime artifacts
DB schema · GraphQL schema · workflow engine · async-work scheduler · authz checks

Seven features partition the spec — each a self-contained YAML block with its own entities, enums, mutations, queries, and (sometimes) workflows: company-management, onboarding, offboarding, documents, payroll, irish-payroll, and revenue-submissions (the operator/daemon-facing layer that drives the async integrations). There are no hand-written CRUD endpoints — the codegen derives GraphQL queries & mutations from entity declarations. Authorisation is declared on each mutation (role + optional relation), and the framework enforces it at the GraphQL boundary so the product code never sees an unauthorised call.

Two declarations carry most of the semantic weight. Workflows declare every state, every transition, and the routing logic between them — so the framework knows which mutations are legal in which state, and can mechanically verify no state is unreachable or missing transitions. Async work specs declare the outbound mapper (DTO → wire), the inbound mapper (wire → DTO), the correlation key, and the post-completion routing — so the framework can generate the AsyncWorkExecution row, the apply-mutation, and the __complete__<name> synthetic transition without product code touching the framework internals.

Why Irish tax rules survived code generation

Irish payroll is famously fiddly — 12 PRSI classes with banded rates and a tapered PRSI credit, 4-band USC keyed off 6 status categories with per-employee overrides, three different tax bases, an annual LPT deduction divided across pay periods, three-party Auto-Enrolment with a 25% state top-up over a pensionable-earnings band. Most of this would normally live in opaque tax-engine code. Here, it lives in typed domain entities — which is what makes code generation possible.

Tax-year configuration → entities, not constants

  • IrishPayrollConfiguration — PAYE standard & higher rates per tax year
  • PRSIBand — one row per class × validity range, with employer/employee rates and weekly thresholds
  • USCBand — one row per status × band, with annualCeiling and rate
  • AutoEnrolmentConfig — AE rates, earnings band, opt-out window, re-enrolment cycle

Every rate carries effectiveFrom / effectiveTo, so Budget changes are a data update — not a code change.

Per-employee parameters → driven by Revenue

  • IrishTaxProfile sourced from RPN (Revenue Payroll Notification)
  • PPSN, tax credits, standard-rate cut-off, USC status — all per-employee
  • Per-employee USC band overrides (uscBand1-4Rate/CutOff)
  • Tax basis modelled as an enum: CUMULATIVE / WEEK1_MONTH1 / EMERGENCY
  • Previous-employment YTD pay/tax/USC/PRSI for mid-year joiners
  • validFrom / validTo bracket each RPN's effective window

Because the calculator reads declared rates from the entity store (not hard-coded constants), the bulk of the Irish payroll math reduces to a deterministic function over typed inputs. Tax basis is an enum the calculator branches on — not a boolean flag tangled through ad-hoc conditionals. RPN data flows through Revenue's own RPN sync (lookupRpnSync / newRpnSync) and lands as IrishTaxProfile fields, so the calculator never has to know about Revenue's wire format. The framework's typed codegen can then guarantee that every IrishTaxProfile field has the right Kotlin type, every enum branch is exhaustive (with compile-time checks for new values), and every workflow state covers every transition. The result: when Irish Revenue publishes the next set of rates, updating them is reduced to inserting new rows with a fresh effectiveFrom.

The heart of the product. 17 wait states + 2 terminal states managing the full processing pipeline. Two flavours of pay run

NORMAL

Standard periodic payroll for a pay period (weekly, fortnightly, monthly).

CORRECTION

Compensating transaction. correctedPayRun references the original. Amounts represent deltas: positive netPay = underpayment owed, negative = overpayment recovery.

Supplementary Earnings & Deductions

The payroll feature ships with first-class entities for one-off and recurring pay adjustments that live outside the base salary. They feed the pay-run calculator automatically — when an entity's effectiveDate falls inside a pay period (and the period is on or before any endDate), the amount is added to gross earnings or to deductions during calculatePayRunWork. PRSI/PAYE/USC are then calculated on the full gross (base salary + supplementary earnings), not the base alone.

Recurring vs one-off. When recurring=true the entity applies to every pay period from effectiveDate until endDate (or indefinitely if endDate is null). When recurring=false the entity applies only to the pay period containing effectiveDate, then is done. Both are independent of pay-run state — admins can create them at any time and they'll be picked up automatically by the next pay run whose period covers them.

5 · Async Integration Architecture

Every external call in this product — Revenue ROS, SEPA bank, NAERSA/MyFutureFund — runs through the framework's AsyncWorkExecution machine. The system never blocks a request on a remote system. Instead, outbound XML is generated, parked on an AWE row in AWAITING_RESPONSE, and the workflow advances only when markAsyncWorkDelivered is called with the response. There are 10 distinct integration points and 3 counterparty simulators.

The async work pattern

1
Workflow transition
Mutation fires an async work spec (e.g. submitAndValidatePSR) with a stable correlationKey.
2
Outbound serialised
Framework calls the outbound mapper. Wire DTO → XML (XSD-validated against pinned schemas).
3
AWE parked
AsyncWorkExecution row created; phase=AWAITING_RESPONSE. XML payload retrievable via Get…Payload query.
4
Operator / daemon delivers
Manual: operator runs simulator CLI, uploads response. File: daemon watches inbox.
5
markAsyncWorkDelivered
Inbound mapper parses response, stamps domain entities, creates ack record.
6
Routing logic fires
Route…Logic reads the ack, decides next state: happy path or *_NEEDS_REVIEW.
Correlation key convention: {asyncWorkName}-{entityId}. E.g. submitAndValidatePSR-12345, lookupRpnForProfile-67890. At most one AWE per (asyncWorkName, entity) is in flight at a time — the framework enforces this.

AsyncWorkExecution phases

CREATED→AWAITING_RESPONSE→DELIVERED→COMPLETED

CREATED is transient. AWAITING_RESPONSE is the steady state where the workflow waits for the external system. markAsyncWorkDelivered drives it through DELIVERED to COMPLETED, at which point the routing logic fires.

Two transport modes — same simulator code

The same process(text, mode) function runs in both modes; only the delivery mechanism differs. The payroll product currently configures all five integrations as Endpoint.Manual.

CURRENT DEFAULT

Endpoint.Manual

Framework parks outbound payload on the AsyncWorkExecution row. Operator drives the round trip via the UI.

  1. UI hits AWAITING_RESPONSE audit row
  2. Operator clicks Download — saves outbound-<correlationKey>-DELIVERING.xml
  3. Operator runs the matching CLI:
    ./gradlew :products:payroll:rosSimulate -Pargs="-i file.xml -m ACCEPT"
  4. Operator clicks Mark Delivered…, drops the -resp.xml file into the drop-zone
  5. Framework applies response → workflow advances

No daemons, no filesystem watching, no env vars. Audit trail is automatic — every download & upload is on the AWE row.

LEGACY

Endpoint.File

Framework writes outbound to a directory; a long-lived simulator daemon polls, processes, and writes the response to an inbox the framework watches.

  1. Start daemon: ./gradlew :products:payroll:runSimulators
  2. Dispatcher writes to $TPS_ROS_OUTBOX
  3. Simulator picks up file (dispatched by filename prefix: psr-, checkrun-, newrpn-, lookuprpn-, bank-)
  4. Simulator writes to $TPS_*_INBOX
  5. Framework's inbox-watch tick picks it up

Audit-trail entities

Every external exchange leaves a durable audit record. These entities are separate from the workflow's domain entities (RevenueSubmission, BankFile, AutoEnrolmentMembership) — they capture the wire-level request/response pair.

What you can reconstruct from audit data

  • Exact XML sent & received for every Revenue exchange (RevenueXmlExchange)
  • Per-payment status from the bank (BankFileAck → individual TxSts)
  • NAERSA per-delivery ack with submissionID = sub-{producingAsyncWork.id} (NaersaContributionAck)
  • Revenue PSR ack with acknowledgementId (RevenueSubmissionAck)
  • AsyncWorkExecution row retains the full phase-transition history, including timestamps for fired-at, delivered-at, completed-at

Apply external response (the inbound side)

Seven distinct apply-mutations, one per integration point. All require PAYROLL_ADMIN. Each follows the same shape:

  1. Validate responseXml is not blank
  2. Find the in-flight AWE by correlationKey, phase = AWAITING_RESPONSE
  3. Parse the response to extract summary detail (without applying)
  4. Call markAsyncWorkDelivered(aweId, responseXml, ctx) — framework drives AWE through DELIVERED → COMPLETED, calls the inbound mapper, fires routing logic
  5. Create a RevenueXmlExchange audit record (operationType, exchangeStatus)
  6. Return summary result

Revenue PAYE Modernisation

Every pay run triggers a PSR (Payroll Submission Request) sent to Revenue via the Revenue Online Service (ROS). The workflow handles async validation, rejection, and re-submission.

Two-way integration:
  • Outbound: generate & submit PSR XML (one per pay run, with one line item per employee)
  • Inbound: SyncRevPayrollNotifications pulls RPNs from Revenue to populate IrishTaxProfile
  • Status polling: CheckSubmission / CheckPayrollRun poll Revenue for async results

Submission status lifecycle

DRAFT → SUBMITTED → RECEIVED → PROCESSING → COMPLETED → ACKNOWLEDGED
↳ REJECTED / FAILED

Entities

RosConfiguration (singleton)

One RosConfiguration per system controls how the product talks to Revenue: the employerRegistrationNumber, optional agentTain, software name/version (Revenue tracks what software submitted each PSR), and a sandboxMode flag for testing against Revenue's sandbox.

SEPA bank file

After PSR verification, submitBankFile fires the submitBankFileWork async work to send a pain.001.001.09 bulk credit transfer to the SEPA bank. The BankFile entity captures the file content, payment count, total amount, currency, and a status (GENERATED → SUBMITTED → optionally FAILED). The bank responds with a pain.002.001.10 status report, captured in BankFileAck with per-payment TxSts.

Per-payment visibility. Because the ack is parsed down to individual TxSts entries, a partially-failed file surfaces in the workflow as BANK_NEEDS_REVIEW and the operator can see exactly which employees' payments were rejected.

Tax calculation overview

Irish payroll processes three statutory deductions on every payslip. The CalculateIrishPayroll mutation computes all three plus AE pension and produces an IrishPayrollResult per employee.

Tax basis matters. A CUMULATIVE employee gets the benefit of unused credits and rate-band carried forward from the year-to-date. A WEEK1_MONTH1 employee is taxed on the period in isolation — useful when there's incomplete RPN data. EMERGENCY applies when no valid RPN exists at all.

Authorization model

Two layers of access control: global roles for admin functions, and relation-based access for self-service and manager views.

Separation of duties in the pay run

Pay run progression deliberately splits work across roles:
  • PAYROLL_ADMIN creates, calculates, submits to Revenue, generates bank files
  • CONTROLLER alone can ApprovePayRun (REVIEW → APPROVED) and MarkPayRunPaid (RECONCILED → PAID — the final action)
This means no single person can take a pay run from creation through to payment.
